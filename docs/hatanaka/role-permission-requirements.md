# 権限管理機能 要件定義書

## 1. 概要

### 1.1 目的

在庫管理システムに管理者、MG、一般の3種類の権限を導入し、ユーザーの役割に応じて閲覧できる画面と実行できる操作を制御する。

誤操作や不正操作による在庫データ、品目マスタデータ、ユーザー権限情報の変更を防ぎ、現場運用に必要な範囲で安全にシステムを利用できる状態にする。

### 1.2 対象ユーザー

| 権限 | 表示名 | 権限コード | 想定ユーザー |
| --- | --- | --- | --- |
| 管理者 | 管理者 | `admin` | システム全体を管理するユーザー |
| MG | MG | `manager` | 現場管理者 |
| 一般 | 一般 | `general` | 現場スタッフ |

### 1.3 前提

- 認証基盤は Supabase Auth を使用する。
- 権限情報は `user_profiles.role` に保存する。
- 権限コードは `admin`、`manager`、`general` の3種類とする。
- 自己登録で作成されるユーザーの初期権限は `general` とする。
- 最初の管理者アカウントは、原則としてDBマイグレーションまたはシードで `admin` に設定する。手動SQLは本番直接実行を避け、緊急時の運用手順として別途承認・記録された場合に限る。
- 権限の設定・変更は管理者のみがユーザー管理画面から行える。
- クライアントから送信された権限値を信用せず、サーバー側でログインユーザーの権限を確認する。
- Service Role キーはサーバー側のみで使用し、クライアントへ露出しない。
- 操作ユーザーの特定は、セッション付きSSR Supabaseクライアントで `auth.getUser()` を実行して行う。クライアントから送信されたユーザーID、メールアドレス、権限値は権限判定に使用しない。

## 2. 権限別機能要件

### 2.1 権限マトリクス

| 機能 | 管理者 | MG | 一般 |
| --- | --- | --- | --- |
| 在庫一覧表示 | 可 | 可 | 可 |
| 入庫登録 | 可 | 可 | 不可 |
| 出庫登録 | 可 | 可 | 不可 |
| 品目マスタ管理：閲覧 | 可 | 可 | 不可 |
| 品目マスタ管理：追加 | 可 | 不可 | 不可 |
| 品目マスタ管理：編集 | 可 | 不可 | 不可 |
| 品目マスタ管理：削除 | 可 | 不可 | 不可 |
| ユーザー管理：閲覧 | 可 | 不可 | 不可 |
| ユーザー管理：権限変更 | 可 | 不可 | 不可 |

### 2.2 管理者

管理者はシステム全体を管理するユーザーとして、すべての画面を閲覧でき、すべての登録・更新・削除操作を実行できる。

管理者はユーザー管理画面から他ユーザーの権限を確認・変更できる。ただし、自分自身が最後の管理者である場合、自分自身を管理者以外へ変更できない。

### 2.3 MG

MGは現場管理者として、在庫一覧、入庫登録、出庫登録、品目マスタ管理の閲覧を行える。

MGは在庫の入庫・出庫を登録できる。ただし、品目マスタを自由に変更できると影響が大きいため、品目の追加・編集・削除は行えない。

### 2.4 一般

一般は現場スタッフとして、在庫一覧のみ閲覧できる。

一般は入庫登録、出庫登録、品目マスタ管理、ユーザー管理を利用できない。誤操作を防ぐため、登録・編集・削除操作も行えない。

## 3. 画面要件

### 3.1 画面一覧

| No. | 画面名 | 管理者 | MG | 一般 | 概要 |
| --- | --- | --- | --- | --- | --- |
| 1 | 在庫一覧 | 可 | 可 | 可 | 全品目の現在在庫を一覧表示する |
| 2 | 入庫登録 | 可 | 可 | 不可 | 品目に対する入庫を登録する |
| 3 | 出庫登録 | 可 | 可 | 不可 | 品目に対する出庫を登録する |
| 4 | 品目マスタ管理 | 可 | 閲覧のみ可 | 不可 | 品目の閲覧、追加、編集、削除を行う |
| 5 | ユーザー管理 | 可 | 不可 | 不可 | ユーザー一覧の確認と権限変更を行う |

### 3.2 ナビゲーション表示

ログインユーザーの権限に応じて、サイドバーやメニューの表示を制御する。

| 権限 | 表示するメニュー |
| --- | --- |
| 管理者 | 在庫一覧、入庫登録、出庫登録、品目マスタ管理、ユーザー管理 |
| MG | 在庫一覧、入庫登録、出庫登録、品目マスタ管理 |
| 一般 | 在庫一覧 |

権限がない画面へのメニュー、登録ボタン、編集ボタン、削除ボタンは表示しない。

### 3.3 権限がない画面へアクセスした場合

権限がないユーザーが直接URL入力などで画面へアクセスした場合は、在庫一覧へリダイレクトする。

対象例:

- 一般が `/inbound`、`/outbound`、品目マスタ管理、ユーザー管理へアクセスした場合
- MGがユーザー管理へアクセスした場合
- MGが品目マスタの追加・編集・削除用URLへアクセスした場合

## 4. 操作制御要件

### 4.1 共通

- 画面上の表示制御だけでなく、Server Action / Route Handler / RPC 実行前にも必ず権限チェックを行う。
- 権限がない更新操作は実行せず、在庫データ、品目マスタデータ、ユーザー権限情報を変更しない。
- 権限チェックは、セッション付きSSR Supabaseクライアントでログイン中ユーザーを特定したうえで、対象ユーザーの `user_profiles.role` をサーバー側で取得して判定する。
- 未ログインユーザーは業務画面へアクセスできず、ログイン画面へリダイレクトする。
- 更新系 RPC は原則として `service_role` のみに `execute` を付与し、`anon` や通常の `authenticated` ロールから直接実行できないようにする。
- Server Action / Route Handler は、セッション付きSSR Supabaseクライアントで操作ユーザーと権限を確認した後、必要な更新のみ Service Role クライアントで実行する。
- `security definer` RPC を作成する場合は、`search_path` と `grant execute` を明示し、想定外ロールからの直接実行を防ぐ。
- 権限がない更新操作はリダイレクトではなく権限エラーとして扱い、データを変更しない。

### 4.2 在庫一覧

- 管理者、MG、一般が閲覧できる。
- 在庫一覧の検索、並び順、表示項目は既存要件に従う。
- 一般ユーザーには入庫登録、出庫登録、品目マスタ管理への導線を表示しない。

### 4.3 入庫登録

- 管理者、MGが登録できる。
- 一般は画面表示、登録操作ともに不可とする。
- Server Action 実行時に `admin` または `manager` であることを確認する。

### 4.4 出庫登録

- 管理者、MGが登録できる。
- 一般は画面表示、登録操作ともに不可とする。
- Server Action 実行時に `admin` または `manager` であることを確認する。

### 4.5 品目マスタ管理

- 管理者は閲覧、追加、編集、削除ができる。
- MGは閲覧のみできる。
- 一般は画面表示、閲覧、追加、編集、削除のすべてを不可とする。
- MGの画面には追加ボタン、編集ボタン、削除ボタンを表示しない。
- 品目追加、編集、削除の Server Action 実行時に `admin` であることを確認する。

### 4.6 ユーザー管理

- 管理者のみがユーザー管理画面を閲覧できる。
- 管理者はユーザー一覧でユーザー名、メールアドレス、現在の権限を確認できる。
- メールアドレスは `user_profiles` には保存しない。ユーザー一覧では、Server Action / Route Handler から Service Role クライアントまたは Supabase Admin API を使用して Auth ユーザー情報を取得し、`user_profiles` と結合して表示する。
- ユーザー一覧は件数増加に備え、ページングを前提とする。
- 管理者はユーザーの権限を `admin`、`manager`、`general` のいずれかに変更できる。
- MG、一般はユーザー管理画面を利用できない。
- 権限変更処理は Server Action 経由で実行する。
- 権限変更時はサーバー側で操作ユーザーが `admin` であることを確認する。
- 管理者が0人になる変更は不可とする。最終管理者の降格や同時更新による管理者不在を防ぐため、権限変更処理はトランザクション内で現在の管理者数と対象ユーザーの変更後権限を確認してから確定する。

## 5. データ要件

### 5.1 `user_profiles.role`

`user_profiles.role` は以下の値のみ保存できる。

| 権限コード | 表示名 | 説明 |
| --- | --- | --- |
| `admin` | 管理者 | 全機能を確認・操作できる |
| `manager` | MG | 在庫一覧、入庫登録、出庫登録を確認・操作でき、品目マスタ管理は閲覧のみできる |
| `general` | 一般 | 在庫一覧のみ確認できる |

既存の `general` のみを許可するDB制約は、3種類の権限コードを許可する制約へ変更する。

### 5.2 初期権限

- アカウント作成画面では権限を選択させない。
- 自己登録で作成されたユーザーは `general` として保存する。
- 初期管理者は原則としてDBマイグレーションまたはシードで設定する。手動SQLは本番直接実行を避け、緊急時の運用手順として別途承認・記録された場合に限る。

### 5.3 権限変更

- 権限変更は管理者のみが実行できる。
- 変更対象ユーザー、変更前権限、変更後権限、変更日時、操作ユーザーを監査ログとして記録する。
- 監査ログは既存の監査ログ基盤が利用できる場合はそれを使用する。未整備の場合は、本機能の実装時に権限変更履歴を記録するテーブルを追加する。
- `user_profiles.updated_at` は権限変更時に必ず更新する。ただし、`updated_at` のみを監査ログの代替とはしない。

## 6. セキュリティ要件

- 権限判定はクライアント側表示制御だけに依存しない。
- 更新系の Server Action / Route Handler / RPC では、必ずサーバー側で権限を確認する。
- RLSを有効化し、クライアントからの直接更新で権限を回避できないようにする。
- Service Role キーはサーバー側のみで使用する。
- Service Role クライアントは権限判定を通過した後のサーバー側更新に限定して使用する。操作ユーザーの認証状態や権限判定を Service Role クライアントだけで行わない。
- ユーザー管理画面と権限変更処理は管理者のみに制限する。
- 権限がないユーザーの直接URLアクセスは在庫一覧へリダイレクトする。
- 不正な権限コードはDB制約とサーバー側バリデーションで保存不可とする。

## 7. 非機能要件

### 7.1 ユーザビリティ

- 権限がない機能のメニューや操作ボタンは表示せず、ユーザーが実行できる操作だけを画面に表示する。
- MGが品目マスタ管理を閲覧する場合、閲覧専用であることが分かる画面表示にする。
- 権限情報は、業務画面の最小共通祖先レイアウトでSSR初回シードし、クライアントでは同一キーでSWR再検証する。
- 権限変更後、対象ユーザーは次回画面表示またはSWR再検証時に新しい権限でメニュー・画面制御される。
- 管理者がユーザー権限を変更した後は、ユーザー一覧と権限情報のSWRキーを再検証対象とする。

### 7.2 保守性

- 権限定義はコード内で重複定義せず、共通定数または共通関数として管理する。
- 権限判定は小さな純粋関数に切り出し、画面表示制御とサーバー側操作制御の双方で同じルールを参照できるようにする。
- TypeScript の型として `admin`、`manager`、`general` のユニオン型を定義する。

### 7.3 品質

- 権限別の表示制御、直接URLアクセス、Server Action の権限チェックをテスト対象とする。
- 権限がないユーザーで更新処理を直接呼び出してもデータが変更されないことを確認する。
- RPC の `execute` 権限が `service_role` に限定されていることを確認する。
- 最終管理者を降格できないこと、同時更新でも管理者が0人にならないことを確認する。
- 権限変更時に監査ログが記録されることを確認する。

## 8. 受け入れ基準

1. `admin`、`manager`、`general` の3種類の権限を `user_profiles.role` に保存できる。
2. 自己登録ユーザーの初期権限が `general` になる。
3. 管理者は在庫一覧、入庫登録、出庫登録、品目マスタ管理、ユーザー管理を利用できる。
4. 管理者は品目マスタの追加、編集、削除ができる。
5. 管理者はユーザー管理画面でユーザーの権限を変更できる。
6. 管理者が0人になる権限変更はできない。
7. MGは在庫一覧、入庫登録、出庫登録を利用できる。
8. MGは品目マスタ管理を閲覧できる。
9. MGは品目マスタの追加、編集、削除ができない。
10. MGはユーザー管理画面を利用できない。
11. 一般は在庫一覧のみ閲覧できる。
12. 一般は入庫登録、出庫登録、品目マスタ管理、ユーザー管理を利用できない。
13. 権限がない画面へ直接URLでアクセスした場合、在庫一覧へリダイレクトされる。
14. 権限がない操作ボタンやメニューは表示されない。
15. 権限がないユーザーが Server Action / Route Handler / RPC を直接呼び出しても、データは更新されない。
16. 不正な権限コードは登録・更新できない。
17. 更新系 RPC は `service_role` 以外から直接実行できない。
18. 権限変更時に変更対象ユーザー、変更前権限、変更後権限、変更日時、操作ユーザーが監査ログに記録される。
19. ユーザー一覧のメールアドレスは Auth ユーザー情報からサーバー側で取得され、クライアントから任意指定された値を表示・保存しない。

## 9. 関連ドキュメント更新が必要な事項

本要件を正式に実装する場合、以下の既存ドキュメントは内容更新が必要となる。

| ドキュメント | 更新理由 |
| --- | --- |
| `docs/design specification/functional_requirements.md` | 現在はロール別アクセス制御を本リリース対象外としているため、対象機能へ変更する必要がある |
| `docs/design specification/account-signup-requirements.md` | 現在は管理者、MGなどのロール別権限管理を対象外としているため、自己登録は `general` 固定のまま、権限管理機能との関係を更新する必要がある |
| `docs/design specification/database-table-design.md` | `user_profiles.role` の制約が `general` のみ許可になっているため、`admin`、`manager`、`general` を許可する設計へ変更する必要がある |
| `docs/design specification/technical-requirements.md` | 業務画面の認証ガードに加えて、ロール別の画面・操作制御方針を追記する必要がある |

## 10. 想定外（本リリースのスコープ外）

以下は将来的に検討する可能性があるが、本要件では対象外とする。

- 部署、拠点、施設単位の権限制御
- 品目カテゴリ単位の権限制御
- 入出庫履歴単位の閲覧制御
- 承認ワークフロー
- ユーザー招待
- ユーザーの利用停止、退会、削除
- パスワードリセット
- 多要素認証
- 詳細な監査ログ画面
